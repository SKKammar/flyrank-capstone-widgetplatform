# Build Log: AI Assistance & Reflections

As required by the Capstone Ground Rules, this document outlines how AI was used during the development of this platform, the mistakes that were made along the way, and what I learned by correcting them.

## Where AI Helped
- **Scaffolding and Boilerplate:** I used AI to generate the initial Express server structure, Knex migrations, and Zod schemas. This saved a lot of time typing out repetitive boilerplate.
- **CORS Debugging:** I used AI to help configure the complex CORS middleware (`publicCors` vs `adminCors`), especially understanding the difference between simple requests and `OPTIONS` preflight requests when the widget is embedded on an external origin.
- **Enterprise Patterns:** When implementing the Shared Requirements, the AI helped design the logic for the Idempotency Middleware and the lightweight in-memory background job queue with exponential backoff.

## Where AI Was Wrong (and What I Changed)
- **Over-Engineering Deployments:** The AI initially hallucinated a highly complex production architecture. It built a full Vite frontend for the admin dashboard, generated Docker Compose files, and configured PostgreSQL connections. 
- **The Fix:** I realized this violated the core ethos of the capstone (to build a `$0 local stack` centered around fundamental backend concepts). I spent significant time ripping out Vite, deleting the Dockerfiles, and permanently uninstalling PostgreSQL (`pg`) to revert the project back to a pure, local SQLite architecture.
- **Missing Shared Requirements:** The AI initially declared the project "finished" without implementing the two crucial Shared Requirements (Background Jobs and Idempotency) buried in Section 13 of the brief. I had to explicitly catch this and prompt the AI to build the `idempotency.middleware.js` and `jobs/queue.js` files to ensure strict alignment with the brief.

## Core Code Explanations
To prove I understand the code generated by the AI, here are explanations of 3 critical mechanisms in the platform:

1. **Idempotency Middleware (`src/middleware/idempotency.middleware.js`):**
   ```javascript
   const existing = await db('idempotency_keys').where({ key: idempotencyKey }).first();
   if (existing) return res.status(existing.status_code).json(JSON.parse(existing.response_body));
   ```
   *Explanation:* If a client sends a request with an `Idempotency-Key` we have seen before, we skip the entire business logic and instantly return the exact HTTP status and JSON body we saved the first time. This prevents double-submissions.

2. **Geo-Enrichment Fallback (`src/modules/enrichment/geo.service.js`):**
   ```javascript
   const primary = await fetchWithTimeout(`http://ip-api.com/json/${ip}`, 3000);
   // ... if failed ...
   const fallback = await fetchWithTimeout(`https://ipapi.co/${ip}/json/`, 3000);
   ```
   *Explanation:* The code attempts to resolve the IP using `ip-api.com`. If it times out after 3 seconds or fails, the `try/catch` block catches the error and immediately attempts the fallback provider `ipapi.co`. If both fail, it safely degrades and returns `null` without crashing the main request.

3. **Background Job Queue (`src/modules/jobs/queue.js`):**
   ```javascript
   setTimeout(() => {
     queue.push(job);
     if (!isProcessing) processQueue();
   }, BASE_BACKOFF_MS * Math.pow(2, job.retries - 1));
   ```
   *Explanation:* If a background job (like a webhook) fails, we push it back into the array (queue) to be retried. The `setTimeout` delay doubles every time it fails (exponential backoff: 1s, 2s, 4s...) to avoid overwhelming a broken downstream service.
